Vaultic

Information Security Policy

Last updated: November 13, 2026

1. Purpose, scope and ownership

This policy describes how Vaultic, a personal self-hosted net worth dashboard, protects the financial data it handles, including data obtained through Plaid. It covers the application, its database, its backups, its source code and its deployment pipeline. The system owner, who is also the sole developer, is responsible for this policy. The system has two household users plus the owner as administrator.

2. Access control

  • Every API endpoint requires authentication. Administrative functions (user management, security log access) additionally require the administrator role.
  • Accounts are created only by an administrator. There is no public sign-up.
  • Passwords must be at least 8 characters with upper-case, lower-case and a digit, and are stored only as bcrypt hashes.
  • Two-factor authentication (TOTP) is required at login. Disabling it requires the account password. The intermediate step after password entry uses a short-lived (5 minute), single-purpose token that cannot be used for general API access.
  • Sessions use signed tokens with unique identifiers and expiry. Logging out revokes the token server-side, and an administrator or user can revoke all sessions.
  • Failed logins are rate limited per IP address and per username, and manual sync actions are rate limited per user.
  • Least privilege: users can only access the application's own data through the application; direct system and database access is limited to the owner.
  • Access review: each month the owner reviews the list of active users and the security log for unexpected activity.

3. Encryption

  • In transit: all access to the application is over HTTPS, and the application connects to Plaid and other services over TLS.
  • At rest: Plaid access tokens and two-factor secrets are encrypted with Fernet before storage, and passwords are bcrypt-hashed. Other application data (such as balances and transactions) is held in the application database without separate application-level encryption and is protected by access controls and the storage protections of the hosting and backup providers.

4. Secrets management

  • Secrets (encryption key, token signing key, API keys) are kept in server environment configuration and are never committed to source control; the repository contains only a template with no values.
  • Secrets are never written to logs or shared in chat or tickets.
  • Secrets are rotated whenever exposure is suspected and at least once a year.

5. Backup and recovery

  • The database is continuously replicated to off-site cloud object storage (7-day retention) and to a local replica (72-hour retention).
  • A documented restore procedure is kept in the repository. The owner performs a test restore at least once a quarter.

6. Logging and monitoring

  • A security log records logins and failures, authentication failures, requests and server events. It rotates automatically with bounded size.
  • System logs are retained for 7 days.
  • Errors on connected Plaid institutions trigger a push alert to the owner.

7. Vulnerability and patch management

  • Dependabot alerts and security updates are enabled for the repository, and weekly version updates are configured for Python, JavaScript and GitHub Actions dependencies.
  • Updates arrive as pull requests and go through the normal automated tests and owner review before deployment.

8. Secure development

  • Every change is tracked in an issue, analyzed before coding, and made in small commits.
  • Automated unit and end-to-end tests must pass in CI before anything is deployed.
  • Coding rules require parameterized SQL, input validation, no stack traces in error responses, a restrictive content security policy and restricted cross-origin access. Security controls may not be weakened without explicit owner approval.

9. Incident response

  1. Detect: alerts, log review, or notices from Plaid or the dependency scanner.
  2. Contain: revoke sessions, rotate affected secrets, remove affected Plaid items, and take the service offline if needed.
  3. Assess: determine what data was affected using logs and backups.
  4. Notify: inform Plaid and affected users within 72 hours of confirming an incident involving their data, or sooner if required.
  5. Recover: restore from backup and verify integrity.
  6. Review: record a post-incident review and follow-up fixes in the issue tracker.

10. Data retention and disposal

Retention and deletion practices are described in the Privacy Policy. Disconnecting an institution removes its Plaid item and access token. User data is deleted manually on request, and backups expire on the schedule above.

11. Personnel

There are no employees or contractors. Access for a person who should no longer have it is removed by deactivating the user account and revoking that user's sessions.

12. Review

This policy is reviewed at least once a year and after any security incident.
